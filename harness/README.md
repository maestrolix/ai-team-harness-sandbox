# AI Team Harness

Самостоятельный Python CLI для GitHub Project: один диспетчер и настраиваемый
пул воркеров. При `--workers 3` три независимые Issue из `AI Open` выполняются
одновременно. Каждая получает отдельный Git worktree, ветку `ai/*` и PR.
Внутри задачи оркестратор вызывает специалистов последовательно.

Runtime использует стандартную библиотеку Python. Для разработки дополнительно
устанавливаются pytest, coverage, Ruff и build. Поддерживаются Linux/macOS,
Python 3.11+, Git, GitHub CLI и Codex CLI; Docker закрепляет Codex 0.163.0.
Windows без POSIX-совместимого окружения не поддерживается: используются flock
и группы процессов.

## Установка и подключение приложения

Установите runtime из этого репозитория в отдельное виртуальное окружение:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install ./harness
.venv/bin/harness --help
```

Установщик `install.sh` настраивает GitHub Project, роли и правила **приложения**.
Исполняемый код harness в приложение больше не копируется. Подробности подготовки
Project и авторизации — в [основной инструкции](../README.md).

Создайте отдельный clone приложения. Его `origin` должен совпадать с `repository`
в конфиге; непроверенное перенаправление публикации в другой репозиторий запрещено.
Скопируйте [пример](config.example.toml) в локальный TOML, заполните GitHub Project,
пути, команду проверок и обязательные CI jobs. Пути отсчитываются от TOML, а не от
папки запуска. Конфиг и токены не включайте в Git.

```bash
# Только опрос и локальная очередь; без модели и записей в GitHub
harness run --config my-app.toml --scan-only

# Один пакет до трёх задач, после завершения выйти
harness run --config my-app.toml --workers 3 --once

# Постоянный диспетчер с тремя слотами
harness run --config my-app.toml --workers 3

# Не более десяти задач; через час перестать принимать новые
harness run --config my-app.toml --workers 3 --max-jobs 10 --max-seconds 3600
```

Для трёх воркеров предварительно настройте изоляцию окружений и укажите
`environment_mode = "isolated"`. Без этого конфиг разрешает только один воркер.
Три задачи должны быть независимыми. Зависимые задачи переводите в `AI Open`
после готовности их зависимостей; автоматического планировщика зависимостей нет.

Также доступны `python -m ai_team_harness` после установки и
`python3 harness/observer.py` из checkout каркаса. Последний файл — только обёртка.

## Параметры

| Параметр | Поведение |
| --- | --- |
| `workers` / `--workers` | Число активных задач; CLI имеет приоритет, по умолчанию 1 |
| `workspace` | Отдельный исходный clone приложения; агенты его не изменяют |
| `state_dir` | SQLite, журналы и worktree; сохраняется между запусками |
| `environment_mode` | `shared` — один воркер; `isolated` — приложение готово к независимым окружениям |
| `poll_seconds` | Интервал опроса GitHub; освободившийся слот вызывает дополнительный опрос |
| `job_timeout_seconds` | Общий бюджет задачи: подготовка, модель, проверки и публикация |
| `check_timeout_seconds` | Дополнительный предел команды проверки |
| `check_command` | Массив аргументов, без shell; запускается в worktree задачи |
| `required_checks` | CI jobs на опубликованном SHA; пустой список сохраняет Draft |
| `trusted_users` | Чьи опубликованные комментарии допускаются к обработке |
| `base_branch` | Необязательная базовая ветка; иначе default branch репозитория |
| `--max-jobs` | Общее число принятых событий за запуск, не число воркеров |
| `--max-seconds` | Срок приёма новых задач; активные заканчивают собственный бюджет |
| `--once` | Один пакет до N независимых событий; свободные слоты далее не пополняются |
| `--retry KEY` | Явно повторить конкретное событие со статусом `blocked` |

Без `--once`, `--max-jobs` и `--max-seconds` процесс работает до остановки.
Ошибки конфигурации и неизвестные ключи отклоняются до обращений к GitHub.

## Устройство проекта

```text
harness/
├── pyproject.toml              # пакет, CLI, зависимости разработки, проверки
├── README.md                   # эксплуатация и архитектура
├── config.example.toml
├── observer.py                 # совместимая точка входа
├── src/ai_team_harness/
│   ├── cli.py                  # параметры запуска и сигналы
│   ├── config.py               # проверка TOML и разрешение путей
│   ├── dispatcher.py           # пул, резервирование, результаты
│   ├── store.py                # постоянная очередь SQLite
│   ├── events.py               # события Issue и пакеты ревью
│   ├── workspaces.py           # изолированные worktree и общие Git refs
│   ├── control.py              # отмена, дедлайн и блокировки
│   ├── processes.py            # команды и остановка групп процессов
│   ├── runner.py               # запуск Codex, schema, журнал JSONL
│   ├── prompts.py              # русские инструкции и контекст события
│   ├── results.py              # проверка JSON-ответа модели
│   ├── workflow.py             # цикл одной задачи и публикация ветки
│   ├── issues.py               # планирование/перенос требований в Inbox
│   ├── publication.py          # ответы ревью и допуск PR после CI
│   ├── github.py               # GitHub REST/GraphQL через gh
│   └── constants.py            # модель и значения протокола
└── tests/                      # модульные и интеграционные проверки
```

Диспетчер — единственный владелец SQLite. Воркеры выполняются в пуле потоков;
каждый запускает отдельный процесс Codex. Python в основном ждёт внешние процессы
и сеть, поэтому отдельный Python-процесс на каждый слот не требуется.

События резервируются по Issue, PR и ветке. Обновление контекста перед запуском
повторно проверяет эти ограничения: перенос PR на занятую ветку не обходит
блокировку. Пакеты ревью одной задачи выполняются по очереди. Неудачная задача
блокирует новые события той же задачи до явного разбора и `--retry`.

У воркера собственный снимок GitHub: изменения вложенных данных не попадают
в соседние задачи. Короткие операции с общими Git refs и создание worktree
сериализованы. Модель, проверки и независимые публикации выполняются параллельно.
Перед публикацией проверяются пауза, доступ, актуальность SHA и замечаний.

Воркер освобождается после публикации результата. Диспетчер продолжает следить
за CI; ожидание человеческого ревью не занимает слот. PR с выполняющимся,
ожидающим или заблокированным событием не переводится в Ready по старому SHA.

## Изоляция окружений

Worktree изолирует рабочие файлы и индекс Git, но не является контейнером или
границей прав ОС. Для каждой задачи harness передаёт процессам:

- `HARNESS_TASK_ID` — стабильное имя `issue-42` или `pr-42`;
- `HARNESS_WORKER_ID` — номер временного слота от 1 до N;
- `HARNESS_WORKSPACE` — абсолютный путь worktree;
- `HARNESS_STATE_DIR` — абсолютный путь состояния;
- `COMPOSE_PROJECT_NAME` — имя, уникальное для пары репозиторий/задача.

Приложение должно использовать отдельные БД, тестовые данные, каталоги сборки,
порты и изменяемые внешние ресурсы. Compose project name помогает разделить
обычные сети и volumes, но не разделяет фиксированные host ports, `external`
volumes и `container_name`. Для их изоляции нужны настройки самого приложения.
`environment_mode = "isolated"` фиксирует этот договор, а не создаёт контейнеры.

Готовьте окружения до запуска или используйте проектные скрипты из инструкции
приложения. Harness не удаляет данные и не выключает сервисы автоматически.
Текущая версия запускает один репозиторий на одной машине; горизонтальное
масштабирование между машинами не реализовано.

## Пауза, сбои и повтор

- `ai:paused` на Issue/PR останавливает её при ближайшей проверке; во время работы
  проверка GitHub выполняется примерно раз в 10 секунд и перед публикацией.
- Файл `PAUSE` внутри `state_dir`, SIGINT или SIGTERM отменяет все активные задачи.
- При отмене и тайм-ауте завершаются группы процессов модели и команд проверок:
  сначала SIGTERM, через ограниченный период — SIGKILL.
- Ошибка одной задачи сохраняет её в `blocked`; другие задачи продолжаются.
- Ошибка опроса GitHub отменяет активные задачи: нельзя продолжать, не имея
  возможности проверить остановку оператором.

Блокировка репозитория наследуется дочерними процессами. Если диспетчер аварийно
завершился, пока такой процесс ещё жив, новый диспетчер не стартует. После
освобождения блокировки прежние `running` переходят в `blocked`, без автоповтора.
Отдельная блокировка защищает каталог состояния от использования вторым процессом.

В `state_dir` сохраняются:

```text
queue.sqlite3             # события и переходы статусов
repository.json           # привязка очереди к clone и GitHub Project
worktrees/issue-42/       # код задачи; не удаляется после ошибки
runs/<event>-<attempt>/   # invocation.json, events.jsonl, stderr.log, result.json, checks.txt
verified/<PR>             # SHA, прошедший локальные проверки
planned/, deferred/      # журналы создания связанных Issue
```

Снимите паузу, изучите журналы и сохранённый worktree. Приведите **эту** рабочую
копию в проверенное чистое состояние, сохранив нужные изменения. Для Issue верните
статус `AI Open`, затем выполните:

```bash
harness run --config my-app.toml --scan-only
harness run --config my-app.toml --retry 'ключ-из-очереди' --once
```

События с неизвестным результатом записи в GitHub не повторяются вслепую.
Проверяйте GitHub и журналы перед повтором. Не удаляйте очередь, attempt-файлы
или ветку ради повторного запуска: это может потерять историю публикации.
Worktree сохраняется для дальнейшего ревью; удаление завершённых чистых worktree
выполняет оператор средствами `git worktree remove`, без `--force`.

## Переход со старого observer.py

1. Остановите старый процесс и дождитесь завершения его дочерних процессов.
2. Сохраните состояние `.state` и изменения старой рабочей копии. Runtime ничего
   не переносит из незакоммиченных файлов в новые worktree.
3. Исходный clone должен быть на основной ветке: одна ветка Git не может быть
   одновременно открыта в нём и в новом worktree задачи. Не используйте force/reset.
4. Установите пакет и укажите тот же clone и `state_dir`. Формат прежних таблиц
   очереди сохранён; `running` после остановки требует явного повтора.
5. Сначала проверьте `--scan-only`, затем один пакет с `--workers 1 --once`.
   После настройки окружений увеличьте workers и включите `isolated`.

Старый установщик копировал runtime в приложение. Новая установка оставляет там
только правила/роли и локальный конфиг. Уже существующие файлы автоматически не
удаляются. Отличающиеся правила согласуются вручную.

## Проверки и покрытие

Из корня репозитория:

```bash
python3 -m pip install -e './harness[dev]'
ruff check harness
ruff format --check harness
python3 -m coverage run --rcfile=harness/pyproject.toml -m pytest harness/tests
python3 -m coverage report --rcfile=harness/pyproject.toml
python3 -m coverage html --rcfile=harness/pyproject.toml
python3 -m build harness
```

Порог CI — **100% строк и ветвей всего пакета `ai_team_harness`**, без исключения
ошибок или модулей из измерения. Тесты охватывают очередь, ревью, планирование
Issue, конфигурацию, сигналы, наследование блокировки, тайм-ауты, восстановление,
CI и публикацию. Интеграционный тест запускает три настоящих процесса через
барьер, реальные worktree, проверки, commit и push в локальный bare remote.

GitHub и ответ модели в автоматических тестах заменены управляемыми адаптерами:
тесты не расходуют токены и не меняют пользовательские репозитории. Покрытие не
доказывает отсутствие ошибок внешних сервисов или корректность приложения.
Команды проверок приложения и человеческое ревью остаются обязательными.

## Docker

[Dockerfile](Dockerfile) собирает wheel отдельным этапом и устанавливает его
в runtime без исходников тестов и инструментов разработки. Процесс работает
пользователем `node` (UID 1000). [Compose](compose.yaml) сохраняет `/state` в volume.

```bash
docker compose -f harness/compose.yaml config --quiet
docker build -f harness/Dockerfile -t ai-team-harness:local .
docker run --rm ai-team-harness:local --help
```

Для работы задайте `HARNESS_CONFIG`, `HARNESS_WORKSPACE`, `HARNESS_GH_CONFIG`,
`HARNESS_CODEX_AUTH`; для числа слотов — `HARNESS_WORKERS`. В контейнерном TOML
используйте `workspace = "/workspace"`, `state_dir = "/state"`. Лимиты ресурсов
можно задать через `HARNESS_MEMORY` и `HARNESS_CPUS`. Подготовка авторизации описана
в основной инструкции. Docker socket не подключается; этот контейнер не создаёт
Docker-окружения приложения. Для Codex требуется поддержка его sandbox на хосте.
